# Work lanes

Use only the lanes required by the user's objective. A lane is an output discipline, not permission to expand the assignment.

## Website

Reproduce the affected route or behavior before editing. Identify the actual source root, hosting provider, nested repositories, active file owners and accepted release. Keep local source, successful build, browser behavior and live deployment separate. Use the existing stack and design system; bounded defects rarely need a rewrite.

For visual work, inspect rendered desktop and narrow-screen states, relevant interaction, keyboard focus, readable text, reduced-motion behavior and an appropriate static fallback. For a model viewer, inspect orbit/reset/preset views and loading/error states. Use rendered artifacts, not a filename or a successful build, as visual evidence.

For a protected research site, check anonymous deep links and original assets as well as the navigation. A hidden index link is not access control. Preserve existing approved access rules. Do not log in as somebody else or expose secrets while testing. Use local or staged fictional fixtures when production mutation is not part of the request.

Deliver exact changed paths, a concise reason, focused validation, screenshots where appearance matters, known limits, and a concrete release candidate. If publishing is authorized, bind the exact destination and artifact/version, execute via the configured provider, then inspect the public result. Otherwise complete the candidate and leave publication as a clear pending action.

## Research

Start with the decision the evidence must inform. Reuse accepted current sources, inspect the decisive source text, and search primary literature, official records or authoritative documentation where new lookup is requested. Do not turn an ordinary literature task into a new scientific program.

Maintain a small evidence table with claim, source URL or local path, date accessed, exact supporting section, study or evidence type, conditions, uncertainty, and what it cannot establish. Cite the actual source rather than another agent's digest. A search hit, abstract, paywall or missing body is not equivalent to full-text inspection. Separate external findings from the project's own measurements.

For quantitative work, state the system boundary, equations, units, inputs and their provenance, assumptions, uncertainty, numerical method, sensitivity and at least one independent or limiting-case check. Label simulated values. Do not turn software tests into biological or physical validation. Keep unknown and rejected results when they remain controlling.

Deliver the source-backed synthesis, a compact source/claim register, consequential disagreements and the next discriminating question. Current project acceptance and publication states change only through their actual authority.

## Brainstorm

Make space for original proposals separately from literature synthesis. If the user asks for brainstorming without search, do not quietly browse. Label the output as ideas with unverified novelty; a new wording or absence from memory is not a novelty result.

For each serious idea, give the mechanism, why it might work, governing constraint, assumptions, strongest failure case, cheapest informative test, and what result would reject it. Rank by a stated criterion. Keep a short rejected-ideas record so the next wave does not rediscover the same failure. Select a candidate only if selection is authorized; otherwise make a recommendation.

Useful output is a few developed, challengeable proposals, not a long list of slogans. Independent criticism should see the proposal and evidence before seeing another reviewer's conclusion when feasible.

## Contact preparation

Identify the purpose and the relevant organization or public professional contact channel. Prefer official contact pages and role addresses; do not infer private personal contact details. Record why each candidate is relevant and the source of the public channel. Do not create or send mail merely because a row has an address.

Prepare individualized, truthful drafts and an attachment/disclosure list. Use a pseudonym or organizational identity only as the user specified. Do not invent a team, affiliation, clinical evidence, investor interest or partnership. Avoid exposing private project details in a public service or model prompt.

Delivery uses an available connector and its actual permission requirements. Follow external-actions.md. An email draft, submitted request, provider acceptance, delivery receipt, inbox observation and recipient reply are separate states. A failed connector should leave a local reviewable draft and exact blocker, while independent work continues.

## Visuals and documents

Choose the appropriate medium. Editable Blender/CAD or native vector geometry is useful for precise repeatable technical views; image generation is useful for illustrative variants. Label concept art and assumed anatomy/geometry. Use the image-generation tool for requested raster creation or editing and inspect references first.

A model must communicate the requested object: for a body-side interface, do not substitute an attractive hand or a large lab rig. Show scale assumptions, relationships, contact paths and necessary sections without inventing qualified anatomy. Keep source model, exports and selected renders tied to the same revision. Never infer manufacturability from a successful render.

For PDFs and presentations, use an installed document/slide/PDF workflow, render the final output, inspect readability, hierarchy, clipping, fonts and figures, then correct observed defects. Give a readable standalone narrative to a reader without prior chat context. Public and private versions should differ by an explicit disclosure map, not by hidden links alone.
